「好好表达」第一次公开 Windows 预览版时，Codex 先准备了一份需要在首次运行时下载语音识别模型的安装包。我想让用户把完整包下载下来，断网也能开始练习。确认模型可以随应用公开分发后，我们换上了内置模型的安装包。下载和安装都验证过，Git 标签却仍指向较早的提交，里面缺少这次构建使用的模型再分发配置变更。[v1.0.1 发布页](https://github.com/morigejile/-/releases/tag/v1.0.1)

## 下载没问题，仍有一个对应关系要核对

Git 标签指向一版源码，GitHub Release 可以挂上供用户下载的安装包。更换附件时，标签仍可以停在原处。这样用户能顺利下载，用标签里的代码追查问题时，却会看到不同的构建条件。下载文件的校验值只能回答两份文件是否一致，构建记录才说明这份文件从哪里来。

下一版先选定准备发布的改动，在独立目录用这份源码快照构建。提交前，Codex 核对暂存的源码与已构建快照一致，标签再指向该提交。安装后用测试样例验证录音回放、重启后读取已有记录，以及内置模型离线初始化。上线后又核对公开附件以及下载文件的校验值。发版记录也保留了发版前的基线提交上同样失败的维护测试。[v1.0.2 发布页](https://github.com/morigejile/-/releases/tag/v1.0.2)

## 我会怎么交代下一次发版

先把「要给用户什么」说具体。例如发布 Windows x64 预览版，下载后可以离线初始化默认模型，另一个还在开发的识别功能继续留在工作区。选定这一版源码后，把模型版本、构建方式和安装包名称记在一起。让 Codex 在安装好的应用里按用户的路径试一遍，最后核对公共下载与本地验证过的是同一个文件。

交付时我最想知道标签落在哪个提交，附件经过了哪些实际验证，还有哪些已知限制。以后遇到安装或初始化问题，我可以先沿着这些信息找到那一次构建，再决定该查源码、随包资源，还是用户的安装环境。
