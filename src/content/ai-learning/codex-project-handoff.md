有一次调整「好好表达」的报告布局，Codex 的对话卡了很久，我开了另一个对话接手。旧对话已经加了一条测试，跑出来却还是失败，工作区里也有之前留下的改动。只说「继续改报告页」，新对话既不知道那条测试是有意先写出来的，还是改动引入了回归，也不知道该以哪个 Demo 为准。

## 先把本轮工作的起点找出来

接手这类任务，我希望 Codex 先读当前分支和差异，再看上一轮最后一次有结果的验证。比如那条布局测试原本要检查一段可选说明在有内容时能紧凑地显示，旧运行里一个对应元素也没有。知道这个失败点，就可以先看渲染有没有实现，再决定该补代码还是查测试。工作区里其余报告和语音识别的改动，也要按原来的归属保留。

现在让我写一条交接消息，我会保留三项信息。

- **从哪里继续。** 仓库、分支、基准提交，以及当时已经存在的未提交改动。
- **以什么为准。** 最新确认的 Demo、截图或产品规则，明确哪些还在讨论。
- **做到哪一步了。** 已改的文件、最后一条测试及其结果，以及下一步应该看哪里。

这些信息足以让接手者先复核现场。历史讨论留在原处，需要理解某个决定时再回去读。

## 分支都绿了，还要看合在一起是什么样

项目早期把评测、模型准备和应用改动放到不同的 Git 工作目录。各条工作线可以独立推进，但不同分支还保留着各自的计划和接口假设。合并后，项目补修了被打破的行为约定，也把文档职责重新理清。现在要查用户能做什么，看需求文档。要查代码怎么运行，看现状架构。下一步做什么，由路线图维护。旧计划留作历史记录，接手时少一处需要猜测的地方。[项目收敛提交](https://github.com/morigejile/-/commit/64a39bfc2e8a7219886bf689fa69daf27aa0bce3)

并行任务各自通过，只能说明各自检出的版本。几条工作线拼起来以后，我还会让 Codex 在合并后的版本跑受影响的完整流程。交付时请它先说清这个结果落在哪个提交、还有哪个环节没验。这样交给下一轮的是可以继续查的项目状态。
